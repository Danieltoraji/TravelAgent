# 多用户改造计划（账号体系 + SQLite 混合落库 + 单 worker 线程池）

## 考察结论（设计依据）

- **a_side 零改动**：A 侧所有会话态都在实例/闭包上（BDecisionHook._current_plan、QuotaManager、LLM 客户端工厂均为 per-instance），不 import runtime 单例。唯一单例依赖在 B 侧 `a_interface.py:29-34`（`_requirement_from_runtime`），且 BDecisionHook 首次 replan 会从 `req.current_timeline` 逆向重建 `_current_plan`——**重启后重建 hook 是安全的**。镜像纪律与 ab_sync 守卫不受影响。
- **改造障碍全在 B/Django 侧**：`agent_runtime.py:598` 模块级单例被 `views.py` 30+ 处直接访问；`init_from_requirement`（:315-331）清空全部内存态并覆写唯一 booking 持久化文件——任何用户新规划会抹掉所有人会话；Django 无 sessions/middleware，全部 `@csrf_exempt`，无任何鉴权。
- **C 端最小接入点已确认**：所有请求经 `TravelAgent-Front/src/services/api.ts` 的单一 `fetchJSON`（:48-80），加一个 header 全端点生效，请求体结构零变化；C 端轮询 = 5s 一轮 `POST /execution/poll/` + `GET /events/?since=N`，重规划感知 = `/replans/` 计数变化（这些语义按用户隔离后原样保留）。
- **并发现状**：gunicorn 1 worker 0 线程（Dockerfile:23，注释明说 workers 必须为 1）；无任何锁；无后台调度——监控全靠 C 端 HTTP 轮询驱动（`poll_once`/`check_lookahead`），这对多租户反而是好事（无全局后台线程要改造）。

## 目标形态

每个注册用户独立持有：requirement、timeline、ExecutionAgent（含决策 hook）、events/replans 历史、预约与 ActionQueue、MockWorld（演示注入只影响自己）。数据落 SQLite，进程重启后用户首次请求时懒重建运行时。gunicorn 单 worker + 8 线程，规划不再互相阻塞；每用户一把锁串行化写操作。

## 阶段 M1：账号与会话基座（运行时隔离）

1. **模型**（`django_server/api/models.py` 新建，挂进现有 `api` app）：
   - `AuthToken`：`user FK→django.contrib.auth User`、`key_hash`（sha256，unique）、`created_at`、`last_seen_at`。key 用 `secrets.token_urlsafe(32)`，只存哈希；密码用 Django 内置 `make_password/check_password`（零新依赖）。
   - `Trip`：`user OneToOne`、`requirement JSON`、`timeline JSON`、`events JSON`、`replans JSON`、`timeline_history JSON`、`booking_state JSON`、`updated_at`（M1 先建表，M2 真正读写）。
   - `manage.py makemigrations api && migrate`；Dockerfile 部署命令前加 migrate 步骤。
2. **认证端点**（`api/auth.py` 新建 + urls 注册，全部免 token）：
   - `POST /api/auth/register/` {username,password} → 建用户+签发 token；`POST /api/auth/login/` → 校验+签发（旧 token 失效可选：单设备语义，直接轮换）；`POST /api/auth/logout/`（需 token）→ 删 token；`GET /api/auth/me/` → username/has_trip。
   - 认证方式：`Authorization: Bearer <key>` 请求头（不用 cookie/session，规避 CSRF 与 Capacitor 明文 http 的 cookie 问题，保持 `@csrf_exempt` 现状）。
3. **运行时管理器**（`django_server/runtime/manager.py` 新建）：
   - `UserRuntimeManager`：`dict[user_id → AgentRuntime]` + 全局锁护字典 + 每运行时一把 `RLock`（暴露 `runtime.lock`）；懒创建：有 Trip 记录则重建（M2），无则空实例。
   - TTL/LRU 淘汰（默认 2h 不活跃、上限 100 个运行时）防内存无界；淘汰只丢内存，真相在 DB。
4. **请求解析中间件**（`django_server/api/middleware.py` 新建，settings.py MIDDLEWARE 注册）：
   - 白名单（`/api/health/`、`/api/auth/*`）外的所有请求：解析 Bearer token → 401 JSON（`{"error":"unauthorized"}`）或挂 `request.auth_user` + `request.runtime`（从 manager 取）+ `request.runtime_lock`。
   - **移除 views 对模块级单例的依赖**：`views.py` 全部 `runtime.xxx` → `request.runtime.xxx`（30+ 处机械替换，成员映射已由考察产出一一对应）；`agent_runtime.py:598` 的单例保留但标记 deprecated（供尚未迁移的旧测试过渡，views 不再引用）。
5. **a_interface 显式传参**：`build_decision_hook(tool_provider, requirement)`、`build_chat_hook(tool_provider, requirement)` 增加必填 `requirement` 参数（保留 `_requirement_from_runtime` 仅作缺省回落）；两处调用点改传 `self.requirement`/`request.runtime.requirement`（agent_runtime.py:199、views.py:840）。**a_side 不动一个字**。
6. **并发**：Dockerfile gunicorn 改 `--workers 1 --threads 8`（注释更新：线程安全靠 per-user 锁 + 单进程内存注册表；workers>1 会串号，必须保持 1）。写端点（plan/timeline POST/chat/poll/lookahead/inject/booking/actions）在视图里 `with request.runtime.lock:` 包裹；纯读端点不加锁。`config/reload` 端点加同锁（全局副作用，文档标注）。

## 阶段 M2：SQLite 落库与重启恢复

1. **Trip 行读写**（agent_runtime 增 `persist()`/`restore()` 两个方法）：
   - 写时机：`init_from_requirement`（requirement+清空后的初始态）、`apply_replan`/`apply_timeline_from_chat`（timeline+replans+history）、每次事件缓冲后（events，仅追加 blob）、booking 状态变更后。统一在既有状态变更点调用，blob 整体覆写（单用户行级数据量小，够用）。
   - 读时机：manager 懒重建——`Trip` 存在 → `parse_timeline_payload` 重建 timeline → `init_timeline`（监控规则自动重建）→ booking_state 灌回 BookingManager → events/replans/history 灌回列表。BDecisionHook 逆向重建机制保证决策链重启安全（考察已确证）。
   - **不持久化**：tool_call_log、hotel 缓存、MockWorld 注入 override、`_last_planner_error`（演示态，丢了无碍）。
2. **BookingManager 存储后端抽象**（booking/booking_manager.py 小改）：把 `_persist`/`_load_persisted` 抽成 `backend.save(dict)/load()`，默认文件后端（现有 `persist_path` 行为、测试全保留），Django 路径注入 DB 后端（读写 Trip.booking_state）。`restore=False` 覆写语义改为"该用户的新计划重置该用户的 booking"，互不影响。
3. **部署持久化**：sqlite 文件路径进环境变量（默认 `django_server/db.sqlite3`）；docker-compose.yml 加 named volume 挂载数据目录（当前无任何卷，容器重建即丢）；deploy.yml 的 `BOOKING_PERSIST_PATH` 标记废弃（文件后端仅存于测试）。

## 风险与明确非目标

- **workers 必须永远为 1**：内存运行时注册表 + sqlite 都按单进程设计，Dockerfile 注释+sync note 双重声明。
- sqlite 并发写：低频（每次 replan/booking 变更一次 blob 覆写），单 worker 线程下够用；不做 WAL/连接池调优。
- 明文 http + 硬编码 SECRET_KEY/DEBUG=True：现状既有债务，不在本期范围（token 明文传输风险与 APK 现状一致，sync note 提示）。
- 不做多 worker 横向扩展、不做用户间共享/社交、不做 Trip 历史（每用户只保留当前行程，新 plan 覆写——与现语义一致）。
- USE_LLM_TOOLS/API key/高德 QPS 预算保持进程级共享：多用户共享同一额度（QuotaManager per-instance 后全局 QPS 纪律弱化，靠 amap_client 10021 退避兜底），演示规模够用。

1. 全量 pytest 绿（本机基线 584+3 个 ab_sync 环境挂不变，新增用例全过）。
2. 本地起服务后：注册两个用户 A/B → A plan（20-70s）期间 B 可同时 plan 互不卡死 → 两边 timeline/events/replans/booking 完全隔离 → 重启进程后 A 带 token 首次请求恢复完整行程与预约状态。

4. 部署冒烟通过（smoke 新清单含隔离抽查）。
