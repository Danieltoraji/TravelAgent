# **TravelAgent——自主旅行管家**

## 一、项目定位（Project Vision）

### 目标

一、项目目标

帮助用户完成整个旅行生命周期，而不仅仅生成一份攻略。

系统具有：

自主规划（Planning）
工具调用（Tool Calling）
长期运行（Long-running Task）
动态重规划（Replanning）
Memory
权限管理（Permission）
Explainable Decision（可解释决策）

## 二、总体架构

整个系统我建议拆成七个模块。

```text
                 User
                   │
                   ▼
          ① Planner（需求解析）
                   │
                   ▼
        ② Task Scheduler（任务规划）
                   │
         ┌─────────┼──────────┐
         ▼         ▼          ▼
     地图Agent  天气Agent  景点Agent
         │         │          │
         └─────────┼──────────┘
                   ▼
          ③ Decision Engine
                   │
         是否需要重新规划？
          │             │
         否            是
          │             ▼
          │       ④ RePlanner
          │             │
          ▼             ▼
      Execution Agent（执行监控）
                   │
                   ▼
          ⑤ Memory（用户偏好）
                   │
                   ▼
      日历/Markdown/APP展示
```

---

## 三、模块职责

### 模块1 Planner

职责：理解用户需求。

例如：

输入：

> 北京两天一夜，预算800，喜欢历史，不喜欢人多。

Planner输出：

```json
{
  "city":"北京",
  "days":2,
  "budget":800,
  "interests":[
      "历史"
  ],
  "avoid":[
      "排队"
  ]
}
```

任务：

* 参数提取
* 缺失信息询问
* 用户画像建立

---

### 模块2 Route Planner

负责：真正生成第一版行程。

例如：

Day1

故宫->景山->王府井->酒店

Day2

天坛->......

输入：Planner结果

输出：时间轴。

这一层不用实时。

---

### 模块3 Tool Agents

这一层全部负责调用API。

建议拆开。

例如：

#### Weather Agent

负责：气温、降雨、紫外线......

---

#### Traffic Agent

负责：公交、地铁、高铁、出租车......

---

#### Scenic Agent

负责：开放状态、预约、排队、营业时间......

---

#### Food Agent

负责：评分、价格、营业、距离......

每个Agent只负责自己的API。

---

#### Booking Agent

负责：所有预约相关能力。

例如：景点预约、酒店预订......

这里只负责准备预约，不负责付款。可以替用户完成信息填写等大多数工作，但是付款必须人工。

## 四、Execution Agent（重点）

这是整个项目最核心。

它负责：

> **持续监控。**

例如：

现在：9:20，还有20分钟到故宫。

Execution Agent：

决定：查询天气、排队等API

不是一直查。

而是：

根据当前时间。

---

## 五、Decision Engine（我建议重点展示）

收到：

Weather Agent：下雨

不能立刻重新规划。先判断影响大吗？

例如：

影响评分：

天气：40

排队：80

交通：20

预算：5

超过阈值才Replan。

否则忽略。

这是整个Agent最智能的地方。

---

## 六、RePlanner

收到Decision Engine：需要重规划。

流程：

重新读取：地图、天气、预算......

↓

重新生成路线

↓

比较新旧路线

↓

生成修改原因

↓

通知用户

例如：

修改:
上午：故宫->景山

原因：故宫预计排队120分钟。

这一块一定要：Explainable。

---

## 七、Memory

保存长期偏好。

例如：

用户：

喜欢摄影

不吃辣

预算紧

讨厌排队

酒店必须四星

以后不用重新输入。

Memory：

自动参与规划。

---

## 八、Monitor（监控任务）

建议不要一个while循环。而是建立Monitor。

例如：

Monitor：

天气：30分钟轮询；

交通：5分钟轮询

景点：到达前20分钟查看

餐厅：到达前30分钟查看

不同事件不同频率。

---

## 九、Permission Manager

负责Agent权限。所有Action先经过manager，再决定：

直接执行

加入Action Queue 等待用户确认后执行

提醒用户自己执行（如付款操作）

---

## 十、Action Queue

建立待执行队列，用户点击确认再执行。

例如：

Today's Actions

✔ 更新路线

✔ 更新日历

□ 预约故宫

□ 预约酒店

□ 购买高铁

□ 支付门票

用户提出旅行目标
        │
        ▼

        │
        ▼

        │
        ▼

## 十、比赛中的展示流程（Demo）

我建议 Demo 不要只是输入一句话然后生成攻略，而是设计一个有"剧情"的演示：

1. **用户提出需求**："北京两天一夜，预算800元，喜欢历史，不想排队太久。"
2. **Agent 解析需求并生成初始计划**，同时展示它调用了地图、天气等工具。
3. **进入执行阶段**，界面显示 Agent 正在监控天气、交通和景区状态。
4. **模拟一个突发事件**：例如天气变成暴雨，或者故宫排队时间从20分钟变成120分钟（可以通过测试数据模拟，而不一定依赖真实 API）。
5. **Decision Engine 分析影响**：说明为什么需要调整，而不是直接修改。
6. **RePlanner 生成新方案**，高亮展示修改前后的区别，并解释原因，例如："将故宫调整至下午，上午改为景山公园，预计节省约90分钟等待时间。"
7. **同步更新日历/Markdown 行程单**，形成完整闭环。

## 十一、建议的开发任务分工

如果是三人的队伍，我建议这样划分：

| 成员 | 核心职责 | 主要模块 |
| ------ | ---------- | -------- |
| A（Agent负责人） | 智能决策 | Planner、Decision Engine、RePlanner、Memory、Prompt、Workflow |
| B（系统负责人） | 工具与执行 | Tool Agents、API封装、Monitor Scheduler、Booking、Calendar、Execution Agent |
| C（产品负责人） | 展示与交互 | Web前端、地图、日志、Action Queue、Permission Manager、Markdown/PDF导出 |

我还有一个建议：设立一位**技术负责人**

他的额外职责不是多写代码，而是：

>维护整体架构图和模块边界；
>定义 JSON 接口格式（例如 Planner 输出、Tool 返回、Action Queue 的数据结构）；
>决定哪些功能进入 MVP，哪些放到后续版本；
>负责最终联调，避免三个人各自开发后接口对不上。

## 总结：最值得重点展示的三个创新点

相比于普通旅游规划工具，我认为你们项目真正的亮点应该集中在这三个方面：

① 持续执行（Execution Agent）

Agent 在旅行过程中持续运行，根据当前行程主动查询相关信息，而不是等待用户提问。

② 自主决策（Decision Engine）

不是任何变化都重新规划，而是先评估影响，再决定是否调整，并给出可解释的原因。

③ 人机协同（Permission Manager + Action Queue）

Agent 可以自主完成查询、规划和准备预约等工作，但涉及预约确认、支付等高风险操作时，会主动征求用户意见。这种权限管理机制既体现了智能体的自主性，也符合真实产品的安全设计理念。

这三个模块共同构成了一个完整的闭环：自主规划 → 持续监控 → 智能决策 → 安全执行。我认为这会比单纯增加更多 API 或功能，更能体现你们项目的 Agent 特性，也更容易在比赛中突出技术深度。
